# وظیفه: اتصال، تکمیل و رفع نواقص پنل ادمین (Admin Panel) و اتصال کامل به بک‌ند NestJS

## ۱. زمینه و چارچوب کلی
ما یک فروشگاه اینترنتی (تجهیزات هوشمند الکتریک) با بک‌ند NestJS 12 و دیتابیس PostgreSQL داریم. UI و ساختار اولیه صفحات پنل ادمین طراحی شده اما برخی قسمت‌ها ناقص است، به API متصل نیست یا منطق بیزینس و فرمت داده‌های آن با قرارداد بک‌ند همخوانی ندارد.
هدف شما: بررسی کامپوننت‌های موجود، حفظ استایل و دیزاین فعلی UI، و پیاده‌سازی کامل لایه سرویس‌ها، فرم‌ها، اعتبارسنجی‌ها و استیت‌ها مطابق مشخصات زیر.

## ۲. احراز هویت و مدیریت نشست (Auth & Session)
۱. **مکانیزم کوکی (HttpOnly Cookies):**
   - احراز هویت با دو توکن `accessToken` و `refreshToken` به صورت کوکی‌های `httpOnly` انجام می‌شود.
   - در تمام ریکوئست‌های کلاینت (Axios یا Fetch) باید حتماً `withCredentials: true` (یا `credentials: 'include'`) فعال باشد تا کوکی‌ها به طور خودکار ارسال شوند.
۲. **بررسی وضعیت ورود ادمین:**
   - اندپوینت `GET /auth/me`: اطلاعات کاربر جاری را به شکل `{ id, name, phone, role }` برمی‌گرداند.
   - اگر کاربر لاگین نباشد (`401`) یا مقدار `role !== 'ADMIN'` باشد، باید دسترسی مسدود و به صفحه ورود هدایت شود (بکند برای نقش غیر ادمین خطای `403 Forbidden` می‌دهد).
۳. **خروج از حساب:**
   - اندپوینت `POST /auth/logout` کوکی‌ها را پاک می‌کند.
۴. **تمدید توکن:**
   - اندپوینت `POST /auth/refresh` برای تجدید نشست در پاسخ ۴۰۱ (توسط Axios Interceptor).

## ۳. ماژول مدیریت سفارشات (Orders Management)

### ۳.۱ لیست سفارش‌ها (`GET /admin/orders`)
- **پارامترهای Query:**
  - `page`: عدد صحیح (پیش‌فرض ۱)
  - `limit`: عدد صحیح (پیش‌فرض ۱۰، حداکثر ۵۰)
  - `status`: فیلتر وضعیت (`PENDING`, `CONFIRMED`, `SHIPPED`, `DELIVERED`, `CANCELLED`)
  - `paymentStatus`: فیلتر وضعیت پرداخت (`PENDING`, `WAITING_REVIEW`, `PAID`, `FAILED`)
  - `search`: جستجو در شماره سفارش (`orderNumber`) یا شماره تلفن گیرنده (`receiverPhone`)
  - `dateFrom` و `dateTo`: فیلتر بازه تاریخ با فرمت ISO8601
- **ساختار پاسخ بک‌ند:**
  ```json
  {
    "items": [
      {
        "id": 1,
        "orderNumber": "SE-9K3P2M8X",
        "status": "PENDING",
        "paymentMethod": "CARD_TO_CARD",
        "paymentStatus": "WAITING_REVIEW",
        "hasReceipt": true,
        "itemsPrice": 320000,
        "shippingPrice": 0,
        "totalPrice": 320000,
        "receiverName": "علی محمدی",
        "receiverPhone": "09121111111",
        "province": "تهران",
        "city": "تهران",
        "addressLine": "خیابان لاله زار پلاک ۱",
        "postalCode": "1111111111",
        "note": "تحویل عصر",
        "trackingCode": null,
        "adminNote": "یادداشت داخلی ادمین",
        "createdAt": "2026-11-08T08:00:00.000Z",
        "paidAt": null,
        "user": { "id": 101, "name": "علی محمدی", "phone": "09121111111" },
        "items": [
          { "id": 1, "productId": 10, "title": "کلید دوپل", "price": 160000, "quantity": 2 }
        ]
      }
    ],
    "total": 45,
    "page": 1,
    "limit": 10
  }
  ```
- **نکات مهم در UI لیست:**
  - فیلد `hasReceipt: boolean` نشان‌دهنده وجود فیش است (فیلد مسیر مستقیم فیش در لیست عمداً حذف شده است).
  - مبالغ به تومان است؛ `shippingPrice` همیشه ۰ است (هزینه پست پس‌کرایه است).
  - بج‌های وضعیت (Badges):
    - برای `paymentStatus === "WAITING_REVIEW"` بج زرد/نارنجی هشدار با آیکون فیش منتظر بررسی نمایش داده شود.
    - برای `status`: `PENDING` (در انتظار)، `CONFIRMED` (تایید شده)، `SHIPPED` (ارسال شده)، `DELIVERED` (تحویل شده)، `CANCELLED` (لغو شده).

### ۳.۲ جزئیات کامل سفارش (`GET /admin/orders/:id`)
- دریافت اسنپ‌شات کامل آدرس، مشخصات کاربر، لیست اقلام سفارش و یادداشت ادمین (`adminNote`).

### ۳.۳ مشاهده/پیش‌نمایش تصویر فیش واریزی (`GET /admin/orders/:id/receipt`)
- تصویر به صورت استریم با هدر امنیتی `Cache-Control: private, no-store` برگردانده می‌شود.
- برای نمایش عکس در Modal یا کادر پیش‌نمایش، حتماً باید ریکوئست تصویر با احراز هویت کوکی ارسال شود (یا به صورت `Blob` واکشی شده و با `URL.createObjectURL(blob)` رندر شود تا هدر احراز هویت ارسال گردد).

### ۳.۴ تایید یا رد فیش واریزی (`PATCH /admin/orders/:id/payment`)
- **شرط مجاز بودن در UI:** فقط زمانی فعال باشد که `paymentStatus === 'WAITING_REVIEW'` است.
- **بدنه درخواست (JSON):**
  ```json
  {
    "action": "approve", // یا "reject"
    "adminNote": "فیش بانکی مطابقت داشت و تایید شد" // اختیاری، حداکثر ۵۰۰ کاراکتر
  }
  ```
- در صورت `approve`: وضعیت پرداخت `PAID`، وضعیت سفارش به `CONFIRMED` و زمان `paidAt` ثبت می‌شود.
- در صورت `reject`: وضعیت پرداخت `FAILED` می‌شود تا خریدار بتواند فیش جدید آپلود کند.

### ۳.۵ تغییر وضعیت پردازش سفارش (`PATCH /admin/orders/:id/status`)
- **نقشه صریح انتقالات مجاز در بک‌ند:**
  - از `CONFIRMED` $\rightarrow$ به `SHIPPED` (الزاماً نیازمند وضعیت پرداخت `PAID` است).
  - از `SHIPPED` $\rightarrow$ به `DELIVERED`.
  - هر انتقال وضعیت دیگر خطای ۴۰۹ برمی‌گرداند؛ دکمه‌ها و فرم UI باید متناسب با وضعیت فعلی فیلتر یا غیرفعال شوند.
- **بدنه درخواست (JSON):**
  ```json
  {
    "status": "SHIPPED",
    "trackingCode": "19876543210123456789", // اختیاری برای SHIPPED، حداکثر ۵۰ کاراکتر
    "adminNote": "تحویل پست مرکزی شد" // اختیاری، حداکثر ۵۰۰ کاراکتر
  }
  ```

### ۳.۶ لغو سفارش توسط ادمین (`POST /admin/orders/:id/cancel`)
- **شرط مجاز بودن:** برای هر سفارشی که هنوز `DELIVERED` یا `CANCELLED` نشده باشد.
- **بدنه درخواست (JSON):**
  ```json
  {
    "adminNote": "لغو به دلیل عدم تطابق آدرس مشتری" // اختیاری، حداکثر ۵۰۰ کاراکتر
  }
  ```
- **منطق:** موجودی تمام اقلام به صورت اتمیک به انبار بازمی‌گردد. اگر سفارش پرداخت‌شده باشد، بکند به یادداشت ادمین تذکر استرداد وجه دستی الصاق می‌کند.

## ۴. ماژول مدیریت محصولات (Products Management)

### ۴.۱ دریافت لیست تمام محصولات (`GET /admin/products` یا `GET /admin/product`)
- لیست کامل محصولات سیستم به همراه محصولات غیرفعال (`isActive: false`) را برمی‌گرداند.
- خروجی: آرایه‌ای از محصولات شامل: `id`, `title`, `slug`, `sku`, `price`, `discountPrice`, `stock`, `isActive`, `categoryId`, `category: { id, name }`, `images`, `specs`, `description`, `metaTitle`, `metaDescription`.

### ۴.۲ جزئیات محصول (`GET /admin/products/:id`)
- اطلاعات کامل محصول بدون فیلتر فعال/غیرفعال.

### ۴.۳ ایجاد محصول جدید (`POST /product`)
- **بدنه درخواست (JSON):**
  - `title`: رشته (۲ تا ۲۰۰ کاراکتر) - الزامی
  - `slug`: رشته با فرمت حروف کوچک انگلیسی، اعداد و خط تیره `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` (حداکثر ۲۲۰ کاراکتر) - الزامی
  - `categoryId`: شناسه دسته (عدد صحیح) - الزامی
  - `price`: قیمت به تومان (عدد صحیح $\ge 0$) - الزامی
  - `discountPrice`: قیمت با تخفیف به تومان (اختیاری؛ در صورت ارسال حتماً باید کمتر از `price` باشد)
  - `stock`: موجودی انبار (عدد صحیح $\ge 0$، پیش‌فرض ۰)
  - `sku`: کد انبارداری یکتا (حداکثر ۵۰ کاراکتر، اختیاری)
  - `description`: توضیحات متنی (اختیاری)
  - `specs`: مشخصات فنی به صورت شیء JSON (مثلاً `{"گارانتی": "۲۴ ماه", "رنگ": "سفید"}`)
  - `metaTitle`: عنوان سئو (حداکثر ۷۰ کاراکتر)
  - `metaDescription`: توضیحات متای سئو (حداکثر ۱۷۰ کاراکتر)
  - `isActive`: وضعیت فعال بودن در سایت (boolean، پیش‌فرض true)

### ۴.۴ ویرایش محصول (`PATCH /product/:id`)
- تمام فیلدهای ایجاد به صورت اختیاری (Partial) قابل ارسال هستند (از جمله تغییر سریع توگل `isActive`).

### ۴.۵ حذف محصول (`DELETE /product/:id`)
- **نکته بسیار مهم:** اگر محصول در گذشته در سفارشی ثبت شده باشد، بک‌ند به جهت حفظ سوابق سفارشات خطای `409 Conflict` با پیام "این محصول در سفارش‌های قبلی ثبت شده و قابل حذف نیست" می‌دهد.
- **رفتار UI:** در صورت دریافت خطای ۴۰۹، یک دیالوگ نمایش دهید که به ادمین پیشنهاد دهد محصول را به جای حذف، **غیرفعال (`isActive: false`)** کند.

## ۵. ماژول مدیریت دسته‌بندی‌ها (Categories Management)

### ۵.۱ لیست دسته‌بندی‌ها (`GET /admin/categories`)
- تمام دسته‌بندی‌ها (شامل غیرفعال‌ها) با دسته‌ی والد (`parent: { id, name }`).
- برای Select والد در فرم‌ها از این اندپوینت استفاده شود.

### ۵.۲ ایجاد دسته‌بندی جدید (`POST /categories`)
- **بدنه درخواست (JSON):**
  - `name`: نام دسته (۲ تا ۱۰۰ کاراکتر) - الزامی
  - `slug`: اسلاگ انگلیسی معتبر (`/^[a-z0-9]+(?:-[a-z0-9]+)*$/`، حداکثر ۱۲۰ کاراکتر) - الزامی
  - `parentId`: شناسه دسته والد (عدد صحیح، اختیاری)
  - `description`: توضیحات دسته (اختیاری)
  - `image`: آدرس تصویر (اختیاری)
  - `imageAlt`: متن جایگزین تصویر (اختیاری)
  - `sortOrder`: اولویت نمایش (عدد صحیح $\ge 0$)
  - `metaTitle`: عنوان متای سئو (حداکثر ۷۰ کاراکتر)
  - `metaDescription`: توضیحات متای سئو (حداکثر ۱۷۰ کاراکتر)
  - `isActive`: وضعیت فعال/غیرفعال (boolean)

### ۵.۳ ویرایش دسته‌بندی (`PATCH /categories/:id`)
- به‌روزرسانی مشخصات دسته یا تغییر وضعیت `isActive`.
- توجه: یک دسته نمی‌تواند والد خودش یا زیرمجموعه فرزندان خودش باشد.

### ۵.۴ حذف دسته‌بندی (`DELETE /categories/:id`)
- اگر دسته‌بندی دارای کالا یا زیردسته باشد، خطای `409 Conflict` می‌دهد. در UI پیغام مناسب نمایش داده شود.

## ۶. نیازمندی‌های تجربه کاربری و مدیریت خطاها (UX & Error Handling)
۱. **پیام‌های Toast و خطاها:** تمام خطاهای ۴۰۰ (اعتبارسنجی فرم)، ۴۰۱ (عدم احراز هویت)، ۴۰۳ (عدم دسترسی)، ۴۰۴ (یافت نشد) و ۴۰۹ (تداخل وضعیت‌ها) باید به صورت Toast فارسی شفاف به ادمین نمایش داده شوند (`error.response.data.message`).
۲. **فرمت اعداد و مبالغ:** نمایش تمام مبالغ با جداکننده سه رقمی و پسوند «تومان».
۳. **تاریخ‌ها:** تبدیل تاریخ‌های ISO8601 به تقویم شمسی (با فرمت ساعت و تاریخ خوانا).
۴. **لودینگ و وضعیت خالی:** نمایش اسکلتون (Skeleton) یا اسپینر در حین لود و پیام «موردی یافت نشد» در جداول خالی.
